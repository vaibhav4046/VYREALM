## Subsequent implementation and local measurements

The audit above and below records read-only research. The following work was performed afterward in the existing VYREALM engine; it does not imply that LongLive or Open-Generative-AI was installed or copied.

- The existing owned-keyframe → visual approval → motion workflow now offers an explicit experimental LTX draft option. Wan remains the default. LTX uses the already-installed `ltxv-2b-0.9.8-distilled-q8_0.gguf`, a fixed 512×288 source, 121 generated / 120 encoded frames, 24 fps, eight sampling steps and tiled decode. Output must pass separate visual review. Provider preflight, source ownership, cancellation, reconnect, hashes and a bounded worker deadline are retained.
- One actual five-second LTX test took **72.648 seconds**, with **4.1006 GiB whole-device peak GPU usage**. It introduced an unwanted hand in the opening second and was **rejected**. A subsequent fresh UI run generated a different Wan keyframe in **195.327 seconds**, reviewed it, explicitly selected LTX, and produced 120 native frames in **61.299 seconds** (**70.473 seconds** for its full motion worker). These stage times exclude operator review and storage-recovery pauses. Its 20 sampled frames show no unwanted hand; full visual review remains separate. Both motion runs had a sampled **4.1006 GiB** whole-device GPU peak. These measurements do not establish cinematic quality or the speed of a complete project. Both 1080p deliveries are separate Lanczos resizes, not native 1080p or AI enhancement.
- Saved-edit batch admission now persists up to 64 explicitly selected distinct project revisions in SQLite. Retries reconcile durable per-entry identities; interrupted admission resumes without duplicate workflows. Actual render, decode and creator-materials jobs use the existing queue. Batch admission does not generate source footage or count unfinished requests as films. The UI separates pending, failed and ready-for-review counts; publishing remains separate.
- A real local editing journey recreated a 30-second portrait Sun film from an existing credited NASA clip: project creation, upload/edit, fresh Piper narration, fresh Whisper captions with operator corrections, automation, complete playback and download. The retained continuous browser recording took **122.106 seconds**, with dependencies and source files already installed. This was imported/edited scientific footage, not neural visual generation. It is a repeat of the same creative film for process evidence, not another unique catalogue film.

Integration fixtures exercise generated-file ownership and actual FFmpeg MP4 encoding with fake providers. They are distinct from the real model run above and must never enter the catalogue as creative outputs. See the following research sections for pinned source revisions and the reasons other candidates remain unqualified.

### Observed system-memory and storage cost

The second run also exposed an operational cost beyond VRAM. On this 16 GB physical-RAM Windows host, the local Python provider was observed at 24.76 GiB private committed memory with 6.07 GiB resident working set after switching models. Windows expanded its system-managed paging file; C: free space dropped from about 7.28 GB to 1.19 GB. These values came from development-console point observations; no continuous RAM trace or timestamped memory snapshot accompanies this report. They are not peak-memory measurements or a claim that the model fits within 16 GB without paging.

The application correctly blocked a motion attempt before invocation when job storage was below its 2 GiB reserve. The exact saved job was retried after obsolete development packages were moved to another volume without deleting projects or source media. Once the provider queue was empty, its supported `/free` operation released idle models and cache. Windows subsequently reduced paging-file allocation and space recovered. No operating-system paging configuration was changed, no active generation was terminated, and no storage threshold was bypassed. A 6 GB GPU reading alone is insufficient evidence of total laptop resource requirements; installations need additional disk headroom for CPU offload and paging.

## What LongLive contributes

The 1.0 design uses causal autoregressive chunks, a rolling local attention window, a retained initial-frame attention sink and KV re-caching when the prompt changes. The paper describes short-window cache refresh and training with the same streaming state to reduce drift. This changes the trained attention behavior: it is not a safe flag to add to VYREALM's existing bidirectional Wan2.2 GGUF sampler. [Original paper](https://arxiv.org/html/2509.22622v1)

Current 2.0 code is based on Wan2.2-TI2V-5B, using AR teacher forcing, DMD few-step distillation, multi-shot sinks, quantized KV and optional streaming VAE decode. The pinned baseline config sets eight latent frames per block, a 32-frame local attention window, sink size eight, four sampling steps, CFG 1 and a 128-latent-frame tensor. Those four steps require the corresponding distilled checkpoint; reducing our ordinary Wan sampler to four steps would not recreate that model. [Pinned config](https://github.com/NVlabs/LongLive/blob/6b36d20ec6f7958d29d11a704dfa64611a9f2572/configs/inference.yaml), [pipeline](https://github.com/NVlabs/LongLive/blob/6b36d20ec6f7958d29d11a704dfa64611a9f2572/pipeline/causal_diffusion_inference.py)

The asynchronous path can overlap VAE decoding with denoising and can move decode to another GPU; immediate CPU transfer of decoded chunks bounds VAE GPU residency. On our one-GPU machine, enabling overlap can increase simultaneous residency, so it needs measurement rather than default activation. [Implementation](https://github.com/NVlabs/LongLive/blob/6b36d20ec6f7958d29d11a704dfa64611a9f2572/utils/inference_utils.py), [runtime docs](https://nvlabs.github.io/LongLive/LongLive2/docs/)

## Open-Generative-AI: useful UX reference, not hundreds of free local models

The pinned application is MIT licensed. Its image/video/audio/cinema workflows mostly call MuAPI with an API key. The implementation reads a browser-stored key and sends generation to api.muapi.ai. That path does not satisfy VYREALM's offline, no-key requirement. ## Concrete next optimization: qualify bounded VAE decode using retained latents

The useful transferable idea is bounded decode memory, not installing LongLive's distributed runtime. VYREALM already has runtime/decode-profiles.mjs with a strict decode-only graph, pinned ComfyUI source and latent ownership/hash validation. Complete that existing qualification before adding another generation backend:

1. Use an already owned 1024×576, 121-frame Wan latent with matching sampler/workflow/source hashes. Do not regenerate the scene.
2. Replay standard decode, then the existing 256-pixel tile / 64-pixel overlap candidate, serially under the existing GPU lease. Keep the temporal parameters fixed and recorded. Do not overlap VAE with a live denoiser on this laptop.
3. Measure each decode independently: wall time, device peak memory, available physical RAM, process working set, system commit and UI responsiveness. Existing whole-generation timing is not an isolated decode baseline.
4. Require the same frame count, dimensions, duration, order and complete FFmpeg decode. Inspect tile boundaries, first/last frames and temporal seams. Compare real-frame SSIM/PSNR and temporal differences against standard decode; numerical similarity alone cannot approve faces/motion.
5. Promote only after the candidate actually reduces memory or latency without a reviewed quality regression. Preserve the original latent/video and show decoded-from-prior-latent provenance. No new native-generation claim.

The development-only `work/github-engine-audit-20260908/verify-decode-fixture.mjs` exercises the current pure graph builder without GPU/model calls and checks no sampler or external nodes enter the replay. The adjacent `qualification-plan.json` describes the unrun hardware experiment; neither file is bundled in the installed runtime. Passing the graph fixture does not measure throughput or qualify the tiled decoder.

## Creator and YouTube automation path

Add scene-boundary proposals as a separate durable CPU analysis job keyed by source hash + detector revision + settings. Restrict input to canonical uploaded media. Analyze downscaled decoded frames with bounded threads and produce ranges only; join the existing raw-footage timeline/edit/review pipeline. A 12-second owned fixture with known cuts at 3, 6 and 9 seconds should return boundaries within one frame, avoid a false cut on a slow pan, invalidate cache when source bytes change, stop on cancellation and leave a playable original. A cut is not evidence of importance; later local transcript-based ranking needs its own labeled evaluation.

Keep publishing separate from offline editing. VYREALM's current youtube-client.mjs already supports private-only resumable upload, file-hash/channel binding and analytics scopes. Reuse it rather than replacing it with a cloud clipping service. Public/scheduled release remains a separate product permission and Google-project audit issue. Google's current videos.insert page says unverified post-July-2020 API projects are private-only and documents a Video Uploads quota bucket; do not promise unlimited publication or reuse old quota numbers. [YouTube upload reference](https://developers.google.com/youtube/v3/docs/videos/insert), [analytics](https://developers.google.com/youtube/analytics/channel_reports)

The repository screening itself copied no candidate code. The measured LTX UI/MCP route and saved-edit batches described above were implemented separately in the existing VYREALM engine.
