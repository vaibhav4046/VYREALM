# Product-owned short/trailer orchestration

The new modules do not generate a film by themselves and do not qualify a model. They connect the ordinary UI production request to the host's existing durable jobs. No standalone Codex provider calls are needed or permitted in the intended user journey.

## Fresh production

`createProductionRun` in `runtime/short-form-production.mjs` takes projectId, expectedRevision, brief, format (`short` or `trailer`), durationSeconds, runId, and shots (`id`, `prompt`, `negativePrompt`, `narration`, `seed`). Shorts are 20–30s; trailers up to 180s; each shot is five seconds. The root service supplies the actual built-in/researched story direction or qualified local planner output. This module does not pretend those supplied prompts were generated by itself.

Optional `firstKeyframe: {shotId,jobId}` adopts the first casting job already created by the ordinary UI service. Its project ownership, actual bytes and exact-hash review must pass the same adapter gate as newly created jobs; it is not automatically approved.

`createShortFormWorker(host)` from `workers/short-form.mjs` returns `tick(runId)`. Invoke after run creation and on job/review completion. It takes a per-run lock, loads canonical state, advances at most three transitions, and stops after enqueue or when review/work remains. No polling or GPU inference happens inside the lock.

The host provides:

- `loadRun(runId)`, `saveRun(state)` and `withRunLock(runId,callback)` using the canonical project store.
- `queueKeyframe`, `queueMotion`, `queueAudio`, `queueRender`: return `{jobId,revision}`. Deduplicate the supplied idempotencyKey durably. Preserve project revision checks, existing output receipts, single-GPU scheduling and cancellation. The module saves intent before queuing; a crash can retry the same key.
- `inspectJob({projectId,jobId})`: return `{jobId,projectId,status,outputHash,assetId,durationSeconds,executionMs,revision,diagnostic}`. Compute hashes and timing from actual durable receipts. Unknown executionMs stays null; do not manufacture zero latency. A motion output must be registered and actually five seconds.
- `verifyReview({projectId,jobId,expectedOutputHash,stage})`: use existing ownership/evidence/byte checks and actual durable review, returning `{verdict,outputHash}`. A technical pass alone is not a visual review. Unreviewed output returns a pending verdict; rejected output returns rejected. Errors indicating corrupt or mismatched evidence must remain errors.

Stage order is keyframe → exact-hash visual review → motion → exact-hash visual review, repeated per shot, then audio → render → final visual review. Rejection stops the run and never silently regenerates or animates failed casting. An explicit new run is required after revised creative direction. Independent generated stills do not establish identity lock; `continuityStatus` remains requires-cross-shot-visual-review.

Audio requests include the exact script and five-second cue windows. Existing Piper's overflow checks must be retained. Derive subtitle end times from its actual speech durations, not by distributing text across silent gaps. Sound design is host-owned and must use the story's events; no generic bed is automatically relabelled as synchronized Foley. The render request includes reviewed shot assets, audio job/hash, fixed format dimensions, and `allowExtension:false`.

Timings separate keyframes, motion, audio and assembly. Missing execution timings are listed explicitly. User-review wait time is not presented as inference latency.

## Existing-footage planning

`runtime/shorts-recipe.mjs` offers `planShorts` using the local Ollama model with JSON output and a metadata inventory. It only runs when sourceMode explicitly equals `existing-footage`; the default fresh request refuses asset substitution. Selection uses the actual inventory supplied by the product, never a hardcoded Rainline clip list. The validator excludes rejected clips and stills, checks 20–30s duration, frame-aligned trims, no overlapping source ranges, and hook/payoff roles. It refuses invalid model output rather than inserting canned copy.

This is metadata-based planning, not visual understanding: descriptions must be derived from trustworthy product/user asset annotations, and the final action/identity/story review remains necessary. Renderer/UI adapters for this optional path are not part of this patch.

## Verification and limits

Tests exercise the host-adapter lifecycle, adopted casting, exact-hash review pauses, rejection, crash/idempotency replay, source insufficiency, and forbidden fresh-to-existing fallback. They are contract tests with controlled jobs, not a generated-video demonstration. The product's actual UI → database → provider → audio → rendered output journey still needs validation after host integration.

No new GPU run, trained model, approved Mahabharata reference or 20–30s finished film was produced by these tests. The active main task owns casting and the single GPU slot. Rejected prior footage is not used as accepted demo content.
